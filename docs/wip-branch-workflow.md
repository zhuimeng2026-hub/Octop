# WIP 分支工作流（未提交改动的快照与重放）

> 状态：**活文档**（最近核实 2026-11-24）
> 文档类型：**规范性文档** —— 规定「线上 / 本机工作树停在半成品状态」时如何留档、如何重放、何时才能清理。
> 落点规则见 [docs/README.md §文档维护规范](./README.md) 第 7 条；分支与发布规则见 `AGENTS.md` §10。

---

## 1. WIP 分支是什么

WIP 分支**不是**功能分支，也**不是**发布分支。它是**一次未提交工作树的快照**，唯一用途是：

1. **不丢东西** —— 把「服务器 / 本机工作树停在某个功能分支的半成品状态」固定成一个可寻址的 commit；
2. **能重放** —— 后续**逐项**重放到 `develop`，而不是整体 merge，把在途快照的脏状态带进主干；
3. **留证** —— 若线上当时跑的就是这份快照，这份 commit 就是「部署被绕过」的现场证据（生产该跑 `v*` tag，见 §5.1）。

快照**不是**上线版本。任何情况下，WIP 分支都不得作为部署来源。

命名：`wip/<主题>` 或 `wip/<主题>-<YYYY-MM-DD>`，主题与对应 issue / 需求同名。

---

## 2. 何时建立

- 线上工作树有未提交改动，且短期内无法在功能分支上收尾；
- 需要把线上在途状态交给本地继续开发；
- 交接、迁移、换机器之前留底；
- 线上部署的代码与 `develop` 不一致，需要一个可引用的版本号。

**不适用**：功能开发本身请用 `feature/*`；已完成的分支清理请用 §5 的判据，不要随手删。

---

## 3. 建立方式（约定）

不要把运行中的生产目录作为默认操作面，也不要直接在其中用 `git add -A` 再切换分支。经明确授权后，先只读核对 tracked / untracked / ignored 状态；按范围挑选路径，确认不含密钥、运行时状态或私有数据，再用独立工作树或安全拷贝留档。

留档必须记录来源 base SHA，以及显式选中路径的新增、修改、删除清单（删除也必须记录，否则重放会丢失删除）。生产密钥不得直接复制；快照也不授权 push、部署或删分支。

在独立工作树或安全拷贝上：

```bash
git switch -c wip/<主题>          # 或 git checkout -b wip/<主题>
git add -- <已核对且获授权的路径>
git commit -m "wip: <一句话说明这批在途改动是什么>"
```

提交信息**必须**写清三件事：

| 项 | 示例 |
|---|---|
| 来源 | 线上 `/opt/Octop` 工作树原停在 `feat/desktop-slim-installer @ bf5994a9` |
| 内容 | 包含 product library 目录批量导入、Windows 免安装 zip 与发布流程调整等 |
| 性质 | **仅作快照，后续需以 develop 为准**；未跑 pre-commit 之类也要写明 |

CRLF 需归一为 LF（遵守 `.gitattributes`）。

---

## 4. 重放规则

- WIP 分支**不整体 merge 进 `develop`**；按项拣选（cherry-pick 或手工重放）；
- 重放时**以 `develop` 为准**，冲突按 `develop` 的口径解决；
- 已发布的 WIP 重放记录放在追踪处，不 amend 已发布提交；清理前可保留 SHA 或历史链接。重放完成后，在追踪记录追加「已重放：<commit / PR>」；
- 迁移编号会随 `develop` 推进而变（例如快照里的 `027` 落地时已成 `028`），比对时要按**内容**而不是文件名判断。

---

## 5. 保留与清理判据

WIP 分支**可以删除**，当且仅当以下三条全部满足：

1. 快照里的每一项改动都已重放到 `develop`，或被明确放弃并在文档里记录；
2. 线上部署**已不再**运行该版本，并已核对每个实际发布过的 ref；
3. 相关文档已更新，不再依赖该分支或该 SHA（历史引用可以保留）。

> **若线上仍在运行该版本，那是流程偏差，不是保留分支的理由。**
> 正确处置是**先把生产更新到正式版本**，而不是延长快照分支的寿命。详见 §5.1。

### 5.1 生产环境只跑正式版本

| 项 | 规定 |
|---|---|
| 允许的部署来源 | `main` 上的 `v*` tag（见 `AGENTS.md` §10「只有 `v*` tags 在 `main` 上是生产」） |
| 禁止的部署来源 | WIP 快照分支、未合并的 feature 分支、工作树里的未提交改动、直接跑 `develop` |
| `develop` 的角色 | **常在的集成分支**——测试通过后走 `release/*` → `main` → 打 `v*` tag，生产再拉该 tag |

线上跑着 WIP 快照，是**部署流程被绕过**的偏差，处置顺序是：

1. 先把生产更新到正式版本（`release/*` → `main` → `v*` tag → 生产 `git checkout` 到该 tag 并重启）；
2. 确认实际服务进程与健康检查跑的就是该版本（仅看 checkout 不足；需核对进程、版本响应或等价运行证据）；
3. 再按 §5 的三条判据删除 WIP 分支，并把 §4.2 之类的实测记录更新为正式版本号。

**不要**反过来：为了让快照分支「有存在理由」而把生产留在快照版本上。

**当前线上（2026-11-25 核实）**：生产工作树 `/opt/Octop` checkout 到 **`v1.5.0`**（`main` 上的 tag，指向提交 `ee2586ed`），`git describe --tags` → `v1.5.0`；`octop.service` 重启后新 PID `1632150`，`/videogen/api/health` → 200。此前线上停在 `develop`（属本表所列的禁止来源），已按上述处置顺序纠正——过程与证据见 [todo.md T-003](./todo.md)。

### 怎么验证「已重放」

```bash
# 该分支相对 develop 独有的提交
git rev-list --count cnb/develop..wip/<主题>
# 按内容比对（+ = develop 里没有这份补丁）
git cherry cnb/develop wip/<主题>
# 逐个关键文件对比内容，而不是只看文件名
git diff cnb/develop wip/<主题> -- <path>
```

注意：`git cherry` 全是 `+` **不等于**工作丢失 —— 重放时往往伴随重编号、重构、拆分，patch-id 对不上；必须落到文件与功能层面逐项核对。

## 6. 与镜像链路（GitHub → CNB）的关系

镜像工作流（`.github/workflows/mirror-to-cnb.yml`）按现有权限与镜像拓扑推送来源 ref；不要直接命令向未核实的 remote 推送生产来源快照。镜像不会自动删除 CNB 多出的 ref；清理前必须核对每个实际发布过的 ref。当前 workflow 的现有例外以配置为准（不要假定已排除 `wip/`）：

```
::error::CNB 与 origin 的引用仍不一致，请人工介入
```

不要把“推送 WIP”或“排除 WIP”写成既有机制；如需变更镜像策略，先按权限和现有镜像配置单独评审。无论哪种，都**不要**用 `--force` 推镜像。
